### 拖拽 bug（用户反馈：点击先弹到 50%，最小位置与 InitWidth 不一致）
**根因**（`SplitView.razor.ts`）：
1. **大小写不匹配**：C# `Init` 传的是 PascalCase 匿名对象 `{ Direction, Max, Min, InitWidth }`，ts 读的是 camelCase `options.direction`/`options.initWidth`，全拿 `undefined` → `direction` undefined 导致 `handler` 永远落到 `modeColumn`；`init` undefined 导致 `refresh()` 设 `width=undefined`。
2. **坐标系混乱**：`modeRow` 用 `panel1.getBoundingClientRect()` 当基准，又减相对 separator 的 `spOffset`，首次拖动跳变。

**修法**：
- ts 侧大小写兼容：`options.direction ?? options.Direction`（max/min/initWidth 同理），不动 C# 侧（避免影响其它调用）。
- 坐标统一以 **wrapper（父容器）** 为基准：`offset = e.pageX - wrapRect.left - sepWidth/2`，再算百分比，消除跳变。
- `getFinalPercent` 用 `Math.min/max` 正确处理 %/px 上下限（原逻辑 px 分支有 bug：`offset > l` 时才对 px 生效，但 offset 是相对 wrapper 的像素，与 `l` 单位混用）。

### 可复用结论
- **Blazor JSInterop 传匿名对象给 TS，属性名保留 C# PascalCase，不会被自动转 camelCase**。`.razor.ts` 附件读参数时要么 C# 侧用小写 key，要么 TS 侧 `?? options.PascalCase` 兜底。
- 拖拽定位要用「容器坐标系」，不要混用「目标元素 rect + 点击偏移」。

## SplitView 拖拽 bug 二次定位（真正的根因）

**重要：`dotnet build` 不编译 `.razor.ts`**。ts 由 `tsup` 单独打包到
`BlazorTemplate.ClientCore/wwwroot/js/shared-project.js`（`npm run build-shared`），
入口 `TsHelper/shared.ts`，`mergeComponents()` 注册到 `window.BlazorProject`。
改 ts 后必须重跑打包，否则运行时仍是旧 js（表现为"改了没效果"）。
容器内无 npm 时可直接跑：
`node node_modules/tsup/dist/cli-default.js --config Shared/BlazorTemplates/BlazorTemplate.ClientCore/TsHelper/tsup.config.ts`
（注意 tsup v8 的 bin 是 `dist/cli-default.js`，不是 `dist/cli.js`）。

**真正的根因（两处）**：
1. **单位/语义不一致**：`DictPage.razor` 用 `<SplitView InitWidth="400px">`（像素），
   而 `Min`/`Max` 默认是 `"30%"`/`"70%"`（百分比）。旧算法把面板宽度写成 `xx%`，
   与实际 px 初始值混用，点击时按百分比重算就发生跳变。
2. **`padding:16px` + 默认 `content-box`**：`getBoundingClientRect().width`（含 padding）
   与 `style.width`（不含 padding）差 32px，绝对坐标换算必然漂移；且 `style.width=undefined`
   会回落成 CSS 的 `50%`，这正是"弹到 50%"的来源。

**最终修法（标准分隔条算法，彻底绕开坐标系/单位/padding）**：
- 拖动改为**增量式**：按下时记录 `start=clientX`、`size=panel1.getBoundingClientRect().width`，
  移动时 `size + (clientX - start)`，夹到 `[minPx, maxPx]`，写 `width: Npx`。
  与滚动、padding、gap 全无关，按下瞬间不跳。
- `Min`/`Max` 经 `toPx()` **按容器实际尺寸换算成像素**（"30%"→容器宽的 30%），
  即用户要求的"计算实际的 30%"。
- CSS：`.view-content` 加 `box-sizing: border-box`（消除 padding 漂移）、`min-width/height:0`；
  `.view-content-first` 加 `flex-shrink: 0`（尺寸不被 flex 压缩）。
- razor：初始尺寸按方向作用（row→width / column→height），不再无条件写 `width`。

**核心教训**：分隔条/拖拽类组件不要用「绝对坐标 → 百分比」换算，用「增量 + 像素」最稳。

## SplitView：ts 未处理 InitWidth，导致初始尺寸被 refresh 夹走

**用户反馈**：ts 没处理 `InitWidth`，会把设置的 `InitWidth` 覆盖掉；`min` 应取 `min(当前 min, initWidth)` 中较小者。

**根因**：上一轮把 ts 里的 `init` 字段删了（理由"初始尺寸由 razor 内联样式负责"），但 `getBounds()`
只用 `Min/Max` 换算边界。只要 `InitWidth` 算出的像素落在 `[minPx, maxPx]` 之外，
`refresh()`（wrapper 的 ResizeObserver 触发）或拖拽时的 `clamp` 就会把它夹走。

**修法**（`SplitView.razor.ts`）：
- 恢复读取：`this.init = Number(options.initWidth ?? options.InitWidth ?? 0.5)`。
- 新增 `getInitPx(total)` = `toPx(this.init, total, total * 0.5)`。
- `getBounds(total)` 改为保证 init 必在区间内：
  `min = Math.min(toPx(this.min, total, 0), init)`；`max = Math.max(toPx(this.max, total, total), init)`
  （max 侧是对称补充：否则 `InitWidth > Max` 时同样被覆盖）。

**验证**（node 复刻边界逻辑对拍，`%TEMP%\sv_bounds_test.js`）：
| 场景 | 旧的 refresh 结果 | 新的 |
|---|---|---|
| DictPage `InitWidth=400`, 容器 1600（30%=480>400） | 480 ❌ 被覆盖 | 400 ✅ |
| `InitWidth=0.2`(比例) vs `Min=0.3`, 容器 1200 | 360 ❌ | 240 ✅ |
| `InitWidth=700` > `Max`(0.7×800=560) | 560 ❌ | 700 ✅ |
| 默认 0.5 / 0.3 / 0.7, 容器 1200 | 600 ✅ | 600 ✅ |

ts 已 tsup 重打包，产物含 `getInitPx` / `Math.min(toPx` / `Math.max(toPx`。

**教训**：**初始值必须落在夹取区间内**，否则任何一次 `clamp` 都会静默覆盖用户配置。
凡是"有初始值 + 有上下界"的组件，边界计算都要把初始值纳入（`min=min(min,init)`、`max=max(max,init)`）。

## 设计结论：字典表**不**做「枚举 ⇄ 字典表」转换，而是共用 lookup 抽象

用户提问：字典表是否应支持枚举转换（枚举存进字典表、取回时返回枚举）。核查代码后的结论：

**不做双向转换。让字典表实现 `ILookupProvider` 并入现有 `LookupService`，枚举与字典互不转换。**

现状接缝（已核对）：
- `ILookupService`（`Lookup/LookupService.cs`）已经是**按 string 键**的统一展示名注册表：
  `GetDisplayString(type, key)` / `GetEntries(type)`，值类型 `LookupEntry(Code, DisplayName)`。
- 枚举侧：源生成器产 `IEnumMeta`（`EnumMetaRegistry`，按 `Type` 为键）→ `EnumLookupProvider<TEnum>`
  （`TypeName = typeof(TEnum).Name`，只收带 `[Display]` 的成员）。
- 消费口：`ColumnInfo.LookupType` 是**可写**属性（getter 默认 `IsEnum ? 类型名 : null`），
  所以列上给个字符串就能切到任意 provider。
- 字典表 `DICT_ITEM(TypeCode/ItemValue/ItemName)` 与枚举**同构**（都是 code→name）。

不建议转换的理由：
1. **双源冲突**：落库后 `IEnumMeta`（编译期）与 `DICT_ITEM` 谁是权威没法定，改显示名要改两处。
2. 丢掉枚举全部价值：`FluentEnumSelect<TEnum>`、`switch` 穷尽、`Enum.TryParse` 都不再可靠。
3. **AOT**：要"按运行时 Type 取回枚举"= `MakeGenericType` = R2 硬阻塞。只能返回 `object`（擦除），
   或让泛型实参由调用方静态写死。注意 `Enum.TryParse<TEnum>(string, out TEnum)`（泛型形式）
   是编译期实例化，**AOT 安全**，可用；带 `Type` 参数的重载才需要额外注意。
4. **两个具体实现障碍**（真去接会撞上）：
   - `LookupService` 的 provider 表是 **static** `ConcurrentDictionary`，`Build()` 里
     `TryGetValue` 命中就跳过、`TryAdd` 之后**永不刷新**；`LoadData()` 的返回值被直接丢弃。
     字典表是可运维修改的数据，进这个 static 缓存 ⇒ 改了不生效，需要加失效/刷新能力。
   - `EnumLookupProvider.LoadData()` 是**故意** `throw NotImplementedException`（元数据构造时已就绪），
     字典 provider 不能照抄，必须自己实现加载与缓存。

落地建议（若要推进）：
- A（主路径）：加 `DictionaryLookupProvider : ILookupProvider`（`TypeName = TypeCode`，数据来自
  `IDictionaryService`），列上 `LookupType = "性别"` 即可像枚举一样解析显示名；同时把
  `LookupService` 的缓存改成可失效（或让字典 provider 不进 static 缓存）。
- B（若要强类型）：只加**单向** `GetEnumAsync<TEnum>(string typeCode, string code) where TEnum : struct, Enum`，
  内部用**泛型** `Enum.TryParse<TEnum>`。
- C（若要枚举当初始数据）：只做一次性"种子/同步"工具 upsert `IEnumMeta.Fields` → `DICT_ITEM`，
  明确 DB 为准、代码只负责初始种子。**不做运行时双向同步**。

## Lookup 加载路径异步化（落地）

用户指出：`BaseLookupProvider.LoadData()` 无法处理异步加载。**根因比"没异步"更严重**——
基类在**构造函数**里同步调 `LoadData()`，异步数据源只能 sync-over-async，Blazor 上有死锁风险。

**核心原则：读同步、写异步。** 读接口（`GetDisplayString` / `GetEntries`）的消费方全在渲染路径上
（`AntTable.razor.cs:124`、`InputBuilder.cs:77`、`Condition.razor.cs:85`、`Group`/`SingleConditionBuilder`），
无法 await ⇒ 它们**只读缓存、绝不触发加载**；加载由宿主 await 一次完成。

### 改动（5 个文件，全在 ClientCore）

| 文件 | 变化 |
|---|---|
| `Lookup/ILookupService.cs` | `ILookupProvider`：删 `IEnumerable<LookupEntry> LoadData()`，加 `ValueTask LoadAsync(ct)` + `ValueTask ReloadAsync(ct)`；`ILookupService` 加 `Task InitializeAsync(ct)` + `Task RefreshAsync(string? type, ct)` |
| `Lookup/LookupService.cs` | `Build()` **只登记不加载**；新增 `InitializeAsync`/`RefreshAsync`；**DI provider 不再写进静态表** |
| `Lookup/BaseLookupProvider.cs` | 构造期不再加载（缓存起始为空）；实现 `LoadAsync`（新鲜期内短路）+ `ReloadAsync`（`SemaphoreSlim` 串行化，整体替换缓存）；派生类改为实现 `protected abstract ValueTask<IEnumerable<LookupEntry>> LoadDataAsync(ct)`；`RefreshInterval` 的 TODO 落地为 `IsFresh` |
| `Lookup/EnumLookupProvider.cs` | `LoadData()` 抛 `NotImplementedException` → `LoadAsync`/`ReloadAsync` 空操作 |
| `Layouts/AppRoot.razor.cs` | 注入 `ILookupService`，在 `OnInitializedAsync` 的**已登录分支**内 `await LookupService.InitializeAsync()` |

### 三个设计要点（都不是可选项）

1. **静态缓存必须与 DI provider 分离**。原 `LookupService.Build()` 把 DI provider `TryAdd` 进
   **static** `ConcurrentDictionary` —— 而 `AddLookupProvider` 注册的是 `Scoped`，
   这既是**捕获依赖**（captive dependency）、又导致**数据永不刷新**。
   现在：静态表只放枚举 provider（不可变、可跨作用域），DI provider 只进实例表。
2. **必须有个 await 预热点**。同步读接口没法触发加载，所以要么宿主动手预热，要么永远读到空缓存。
   选在 `AppRoot.OnInitializedAsync` 的已登录分支：字典 API 是 `Authorize = true`，登录前调必失败。
3. **单 provider 失败不能拖垮启动**。`InitializeAsync`/`RefreshAsync` 走 `SafeLoadAsync`：
   捕获非取消异常并 `logger?.LogError(...)`（`ILogger<LookupService>` 可选解析，不引入硬依赖），
   该 type 退化为"显示原始 code"。

**验证**：`ClientCore`、`BlazorTemplate.UI.AntBlazor`、`BlazorAdmin.Client` 均 `-f net8.0 --no-incremental` 构建
**0 error**（61 warning 为既有基线，改动未新增）。生成器产出的
`new EnumLookupProvider<TEnum>(meta)` + `AddEnumProvider(...)` 签名未变，生成代码无需改。

## 追加要求：刷新必须「无感」

用户追加约束：刷新应该是无感的。拆成四条并逐条落地：

| 要求 | 实现 |
|---|---|
| 刷新期间**不能空窗/半成品** | `ReloadAsync` 加载期间**完全不碰缓存**，拿到全量后才 `cache = ...ToFrozenDictionary(...)` 一次性换指针；读侧无锁、永远读到完整字典 |
| 失败要**静默回退** | 只有 `LoadDataAsync` 成功返回后才写 `cache` 与 `loadedAt`；抛异常则两句都跳过 ⇒ 沿用旧数据、`IsFresh` 不推进（下次自动重试），对外"什么都没发生" |
| 并发刷新要**合并**，不重复取数 | 进 `SemaphoreSlim` 前记 `startedAt`，拿到锁后 `if (loadedAt >= startedAt) return;` —— 排队期间已被别的调用刷过就直接复用 |
| 调用方**不被阻塞**、界面**自己能更新** | 新增 `ILookupService.RefreshInBackground(type)`（触发即忘）与 `event Action<string>? Changed`（缓存被替换后触发，参数为 `TypeName`）|

**两个易漏点**：
1. `Changed` 通知必须放在 `SafeLoadAsync` 的 **try 之外**——否则订阅方抛的异常会被误记成"加载失败"。
2. **`RefreshInBackground` 不能直接 `_ = RefreshAsync(type)`**：`SafeLoadAsync` 的异常过滤器是
   `ex is not OperationCanceledException`，而 **HTTP 超时抛的是 `TaskCanceledException`（属 OperationCanceledException）**，
   会逃出去变成未观察的 Task 异常。必须再包一层 `RefreshInBackgroundAsync` 全捕获（记 `LogDebug`）。

`Changed` 事件目前**未接消费方**——订阅它即可让已渲染的界面无感更新（没有 loading 态但内容已是新的）。

### 实测发现的硬缺陷：`new Task(...)` 是冷任务（探针工程 `.workbuddy/tmp/taskprobe/`）

复刻 `BaseLookupProvider` 构造函数的写法对拍：

| 写法 | 结果 |
|---|---|
| `new Task(async () => {...}, TaskCreationOptions.LongRunning)`（原样，未 `Start()`） | 循环体**从未进入**，`Status = Created` |
| `Task.Factory.StartNew(async () => {...}, CancellationToken.None, TaskCreationOptions.LongRunning, TaskScheduler.Default).Unwrap()` | 正常执行，`RanToCompletion` |

同源问题：`async` lambda 绑定到 `Task(Action)` 重载 = **async void** ⇒ `LoadDataAsync` 抛异常即未处理异常
（崩进程），`loadTask` 也无法反映失败。其余待收敛：`DisposeAsync` 对未完成的 `loadTask` 调 `Dispose()`
会抛 `InvalidOperationException`；`loadCts is null` 恒 false；`RefreshInterval` 只判 `== TimeSpan.Zero`，
负值语义与注释不符；fire-and-forget 无可 await 点 ⇒ 首帧仍可能读空缓存（原 `InitializeAsync` 的作用）；
`ILookupService.cs` 顶部 `using System.Collections.Frozen;` 已无用。
→ 细节与结论已写入 `AOT-DETAIL.md`，**未替用户改 `BaseLookupProvider`**（保留其迭代节奏）。

### 可复用教训

**`Task` 的构造函数 = 冷任务，必须 `Start()`（或改用 `Task.Factory.StartNew` / `Task.Run`）；
`TaskCreationOptions.LongRunning` 只有经「构造 + Start」或 `StartNew` 才生效。**
另：把 `async` lambda 传给 `Action` 参数（`Task(Action)`、`Action` 事件、`List.ForEach` 等）= `async void`，
异常无法被观察。要返回可等待任务，用 `Func<Task>` 重载 + `Unwrap()`。

## 方案：字典表 lookup 不做「一类型一 Provider」

用户提问：按当前设计 `DictionaryLookupProvider` 一个字典类型就得实现一个 Provider，怎么优化（只要方案，不改代码）。

**卡点（代码依据，已核对）**：
1. `ILookupProvider.TypeName` 是**单值实例属性** + `BaseLookupProvider` 持单份缓存 ⇒ 天然一类型一实例。
2. **真正的接口卡点**：`GetDisplayString(key)` / `GetEntries()` **没有 `type` 参数** ⇒ 多类型共用一个
   provider 时，`LookupService` 层无法把 type 传进去。
3. `LookupService.Build()` 只在**构造期**跑一次并把 provider 冻结成 `FrozenDictionary`（精确匹配）⇒
   **运行期新增的 typeCode 没有任何注册入口**，所以「不在 `Build()` 时展开类型清单」是硬要求。
4. 数据源侧（`DefaultDictionaryService`）：`GetDictTypesAsync()` 一次拿全部类型（`ParentId is null or "ROOT"`）；
   `GetDictItemListAsync` 是**按 parent + 分页**（`.Paging(req.PageIndex, req.PageSize)`）⇒ 拿「某类型全量
   条目」需递归 N 层 × 分页，**不适合启动全量预热**。
5. `IDictionaryService<TDictItem>` 是 `[WebController(Authorize=true)]` ⇒ 每次调用都是 HTTP（客户端代理）。

**方案 1（推荐）：单源 + 未命中兜底路由。** 注册的不是「每类型一个 provider」，而是「一个能按 type 现取的源」：
新增可选接口 `ITypedLookupProvider { GetDisplayString(type,key); GetEntries(type); }`（**不动** `ILookupProvider`）；
`LookupService` 命中精确表走原路、未命中遍历动态源；`DictionaryLookupProvider` 单实例 + `type → {code → name}`
分组缓存，类型清单来自 `GetDictTypesAsync()`、条目按需加载。收益：1 类 / 1 注册 / 1 缓存 / 1 刷新循环替代 N 份，
全静态类型（无 `MakeGenericType` / `Activator`）AOT 安全。代价：同步接口 + 懒加载 ⇒ 首次访问某 typeCode
读不到数据、退化为显示原始 code，需约定「谁触发加载」。

**方案 2（类型集稳定时更优）：类型清单源生成器 + 泛型 provider。** 关键观察：**不稳定的只是条目，类型集合
通常稳定**。把类型清单放进代码（`DictCodes` 常量类），生成器产 N 条静态注册（同 `AddEnumProvider` 套路），
一个 `DictionaryLookupProvider<TDictType>` 服务一类 ⇒ `TypeName` 编译期可知、可静态注册、可启动预热（无首帧
问题）、可给 `FluentEnumSelect` 用。代价：新增类型要改代码重编译。与方案 1 可叠加（精确表优先、动态源兜底）。

**方案 3（不推荐）：type 编进 key**（`"{type}\x1f{key}"`）。零接口改动，但 `GetEntries(type)` 仍要分组、
type 语义藏进字符串，只适合临时打通。

**落地清单**：① `LookupService` 加未命中→动态源路由（必要）；② 新增 `ITypedLookupProvider`；
③ `DictionaryLookupProvider` 注入 `IDictionaryService<TemplateDictItem>`（`TemplateDictItem` 静态写死保 AOT）；
④ **服务端补一个「按 typeCode 一次拉全量条目」的不分页不分层接口**，否则客户端要递归 + 分页拼树（N 次 HTTP）；
⑤ 定「树 → 平铺」取层规则（`ColumnInfo.LookupType` 消费的是平铺 code→name：取直接子节点还是全部后代）；
⑥ 加载策略改「类型清单预热 + 单类型懒加载 + 写后定向失效」，**不要**复用 `BaseLookupProvider` 的构造期全量
自驱（N 类型 × 递归 × 分页 = 启动打满 HTTP）；⑦ 若仍复用 `BaseLookupProvider`，先修其冷任务缺陷。

## 框架样式与组件库 token 的桥接（CSS 变量方案）

**背景**：框架自定义组件（SideBar/NavTabs/Banner 等）的样式要与 AntDesign 组件样式同步。

**用户明确的设计口径（关键，我之前理解反了）**：
- 桥接方向 = **框架变量引用组件库 token**，即 `--wb-*: var(--ant-*)`。
- 组件库是**上游**、框架是**下游**；框架样式就是要依赖组件库。
- 换 Fluent 等其它组件库时，改的是 tokens.css 里这些变量的**值**（映射到新库 token），
  **不是**改框架组件的引用。默认值兜底：`var(--ant-*, 默认值)`。

**最终结构**：
```
tokens.css  :root { --wb-primary: var(--ant-primary-color, #1890ff); ... }   ← 唯一事实来源，映射+兜底
框架组件    引用 var(--wb-*)
ant-color.js changeColor() 只写 --ant-*（组件库 token 是上游），衍生色板 -1~-7 仍 JS 生成
app.css    旧变量(--major-color/--font-color/--bg...) 映射为 var(--wb-*) 兼容别名
```

**落地文件**：
- `BlazorAdmin/wwwroot/theme/tokens.css`（新）：`--wb-*` 全集，值 = `var(--ant-*, 默认值)`；
  暗色由 antd dark.css 覆盖 --ant-* 自动跟随，tokens.css 的 dark 块只补阴影/水印非 token 项。
- 删除上一轮方向错误的 `theme/bridge.ant.css`（`--ant-*: var(--wb-*)` 是反的，已撤）。
- `app.css`：`@import theme/tokens.css`（不再引 bridge）；`:root` 旧变量改 `var(--wb-*)` 兼容别名。
- `ant-color.js`：`changeColor()` 恢复写 `--ant-*`（上一轮误改成写 --wb-* 已回退）；
  `initializeColors()` 去掉反向 setProperty。
- `NavTabs.razor.css`：硬编码 `#f5f5f5`/`rgb(64,158,255)` → `var(--wb-bg-hover)`/`var(--wb-primary)`。

**教训**：CSS 变量桥接方向要遵循"框架依赖组件库"的口径（组件库 token 是上游），
不是"框架是唯一事实来源、组件库来桥接"。`--wb-*: var(--ant-*, 回退)` 是正确形态。

### 二次修正：桥接必须在组件库侧，宿主零组件库痕迹（最终方案）

用户两条追加口径：
1. **宿主（BlazorAdmin）不应出现任何组件库 token**（`--ant-*` 等），框架变量默认值必须纯框架概念。
2. **桥接放在组件库侧**（`BlazorTemplate.UI.AntBlazor`），载体用 **JS 运行时桥接**（复用现有
   `ant-style.js` 的 `updateTheme` 思路），而非 CSS 文件。

**最终架构**：
```
宿主 BlazorAdmin/wwwroot/theme/tokens.css
  :root { --wb-primary: #1890ff; ... }         ← 纯框架默认值，零组件库痕迹
  html[data-theme='dark'] { ... }              ← 仅作无组件库时的兜底暗色
  App.razor <VLink Href="theme/tokens.css">    ← 在 @UIService.AddStyles() 之前加载
  app.css :root { --major-color: var(--wb-primary) } 兼容别名（JS 失败时的兜底）

组件库 BlazorTemplate.UI.AntBlazor/wwwroot/ant-color.js
  frameworkVariableMap: { '--wb-primary': '--ant-primary-color', ... , 兼容别名也直接映射 }
  bridgeFrameworkVariables() = 遍历 map, setProperty(frameworkVar, `var(${libToken})`)
  initializeColors() 里调用 bridgeFrameworkVariables()
```

**关键点**：
- JS 写 `document.documentElement.style`（内联 style），优先级最高，覆盖一切样式表规则。
  → `--wb-* = var(--ant-*)`，暗色由 antd dark.css 覆盖 `--ant-*` 自动跟随，运行时改主色 changeColor 也自动跟随。
- 桥接载体 = JS（复用 ant-color.js 已有的 initializeColors 入口），**不用 CSS 文件**（bridge.ant.css 已删）。
- ant-style.js 的 `window.updateTheme(map)` 是预留但**未被调用**的死代码，本轮未启用，直接新增了
  `bridgeFrameworkVariables` 复用 setProperty 机制。

## 暗色主题失效：根因是 JS 内联桥接压过了 data-theme 暗色块

**症状**：收拢变量后暗色主题失效（框架组件不随暗色切换）。

**根因**：上一轮用 JS `document.documentElement.style.setProperty('--wb-*', 'var(--ant-*)')` 做桥接，
内联 style 优先级最高，**压过了 tokens.css 的 `html[data-theme='dark']` 暗色块**。而 antd 的 dark.css
是直接覆盖组件样式、**并不重定义 `--ant-*` 变量**（`--ant-*` 只由 variable.css 定义，且 `setDark()` 里的
`resetThemeVariables()` 还会把 `--ant-*` 重置成亮色）。所以 `--wb-*` 桥接到 `--ant-*` 后，暗色下拿到的
仍是亮色值 → 框架组件暗色失效。

**关键认知**：antd 的暗色是 `ant-design-blazor.dark.css` 直接覆盖组件样式，**不经过 `--ant-*` 变量**。
框架组件的暗色必须靠自己的 `html[data-theme='dark']` 块，不能依赖 `--ant-*` 跟随。

**最终修法**：
1. 删掉 JS 内联桥接（`frameworkVariableMap` + `bridgeFrameworkVariables()` + `initializeColors` 里的调用）。
2. 桥接改回**组件库侧 CSS 文件** `bridge.ant.css`，选择器用 **`html:not([data-theme='dark'])`**（特异性 0,1,1）：
   - 亮色：`html:not([data-theme='dark'])` 匹配，特异性 0,1,1 > tokens.css `:root` 0,1,0 → 桥接覆盖默认值，`--wb-* = var(--ant-*)`；
   - 暗色：该选择器不匹配，tokens.css 的 `html[data-theme='dark']`（0,1,1）生效 → `--wb-*` 用暗色值。
   **用特异性而非加载顺序解决优先级**，不依赖加载顺序，暗色也不会被桥接冲掉。
3. `bridge.ant.css` 接入 `UIService.AddStyles()`（在 ant.css 之后）。

**复用教训**：
- 桥接框架变量与组件库 token 时，若组件库暗色是"直接覆盖样式"而非"重定义 token 变量"，
  框架变量桥接必须用 `html:not([data-theme='dark'])` 限定亮色，否则内联/高特异性桥接会压死暗色块。
- 内联 style 桥接（`setProperty`）优先级最高，会压过所有样式表规则（含 data-theme 暗色），
  这是暗色失效的典型陷阱；静态 CSS 桥接 + 选择器区分亮暗才可控。

## 最终方案：JS 内联桥接（不用 CSS 桥接，暗色写默认值）

**用户最终口径（推翻上面的 CSS 桥接方案）**：
- **不用 CSS 桥接**，回到 JS 内联桥接。
- 暗色没有 `--ant-*` 变量时，JS 桥接直接写**默认暗色值**。
- 改变亮暗模式、改变主题色，**都要重新调用 JS 桥接**。

**最终架构**：
- `ant-color.js` 里 `frameworkVariableMap`：每个框架变量 `{ token, dark }`——
  `token` = 亮色下的 antd token（可 null），`dark` = 暗色默认值（具体色值）。
- `window.applyFrameworkBridge()`：读 `documentElement.dataset.theme` 判断亮暗——
  暗色写 `cfg.dark`；亮色有 token 写 `var(token)`、无 token `removeProperty`（回退 tokens.css 默认值）。
- 三个触发点都调 `applyFrameworkBridge()`：
  1. `initializeColors()`（初始化）
  2. `ant-style.js` 的 `changeTheme()`（切亮暗，设置 data-theme 后）
  3. `changeColor()`（改主题色，写完 --ant-* 后）
- 删掉上一轮的 `bridge.ant.css` 及其在 `UIService.AddStyles()` 的引用。

**关键点**：
- `applyFrameworkBridge` 定义在 ant-color.js，`setTheme`/`changeTheme` 在 ant-style.js；
  加载顺序 ant-color.js 在前（UIFrameworkJs 里先引），且 changeTheme 里用 `if (window.applyFrameworkBridge)` 防御。
- 暗色下 `--wb-*` 与 `--ant-*` 完全脱钩（写死暗色默认值），所以 `setDark()` 里 `resetThemeVariables()`
  把 `--ant-*` 重置成亮色**不影响**框架变量。
- tokens.css 保留 `:root` 默认值 + `html[data-theme='dark']` 暗色块，作为 JS 未加载时的纯 CSS 兜底。

## 定稿：切回 CSS 变量桥接（当前生效方案）

**用户决定切回 CSS 桥接**（JS 内联桥接方案弃用）。当前生效形态：

- **组件库侧** `BlazorTemplate.UI.AntBlazor/wwwroot/bridge.ant.css`：
  `html:not([data-theme='dark']) { --wb-*: var(--ant-*, 默认值) }`，
  只桥接「有 antd token 对应」的变量；无对应的（`--wb-success-bg`/`--wb-fill-*`/`--wb-shadow` 等）交给 tokens.css。
- **宿主** `tokens.css`：`:root` 默认值 + `html[data-theme='dark']` 暗色块（不变）。
- **app.css**：`:root` 兼容别名 `--major-color: var(--wb-primary)` 等（跟随 --wb-*）。
- `UIService.AddStyles()` 引入 bridge.ant.css（ant.css 之后）。
- 已删除：ant-color.js 的 `frameworkVariableMap` + `applyFrameworkBridge`；
  ant-style.js `changeTheme` 里的桥接调用；`initializeColors` 里的桥接调用。

**工作原理（优先级）**：
- 亮色：`html:not([data-theme='dark'])`（0,1,1）> tokens.css `:root`（0,1,0）→ `--wb-*` = var(--ant-*)。
- 暗色：bridge 不匹配，tokens.css `html[data-theme='dark']`（0,1,1）→ `--wb-*` 用暗色值。
- **靠特异性而非加载顺序**，暗色不被桥接冲掉。

**两方案对比（供切换参考）**：
| 维度 | CSS 桥接（当前） | JS 内联桥接（已弃） |
|---|---|---|
| 载体 | bridge.ant.css（组件库侧） | ant-color.js 运行时 |
| 优先级 | 可调（0,1,1），能分层 | 内联最高，压过一切 |
| 切主题 | 选择器自动重算 | 必须手动重调 |
| 暗色无 token | 需 `html:not()` 排除亮色 | `if` 判断直接写值 |
| 值集中度 | 分散（bridge + tokens 暗色块） | 集中在映射表 |

## Bugfix：亮色主题下菜单选中项"底字同色"看不见

**现象**：亮色主题，antd 菜单（left inline Menu）选中项背景色与文字色相同 → 文字看不见。

**根因**（已用 node 复现）：`ant-color.js` 的 `colorPalette(color, index)` 用「提高 HSV 明度」
生成浅色。品牌色如 `#1890ff` 的 `V` 已经 = 1（最亮），提亮被 clamp 回原值 ⇒
`colorPalette('#1890ff', 1..5)` 全部返回 `#188fff`（≈主色）：
```
#1890ff => 1:#188fff 2:#188fff 3:#188fff 4:#188fff 5:#188fff ...
```
antd 的 `.ant-menu:not(.ant-menu-horizontal) .ant-menu-item-selected { background-color: var(--ant-primary-1) }`
+ `.ant-menu-item-selected { color: var(--ant-primary-color) }` ⇒ 底/字都是主色。
触发路径：切到亮色（`AntSetting.UpdateSysMode` → `changeColor(App.MainThemeColor)`）或改主题色。

**修复**：`colorPalette` 改为「与白/黑按比例混合」——
1~5 向 `#ffffff` 混（权重 0.9/0.7/0.5/0.3/0.1），6 = 主色，7~10 向 `#000000` 混（0.1/0.2/0.3/0.4）；
新增 `mixColor(color, target, weight)`。修复后：
```
#1890ff => 1:#e8f4ff 2:#badeff 3:#8cc8ff 4:#5db1ff 5:#2f9bff 6:#1890ff 7:#1682e6
```
（与 antd 官方 1:#e6f7ff / 6:#1890ff 基本一致，够用）

**顺带修好**：`--wb-primary-bg`（= `var(--ant-primary-1)`）作选中底色的地方 → DictPage
`.dict-type-item.active`、SplitView 分隔条 hover。

**遗留**：`adjustBrightness`/`adjustSaturation`/`rgbToHsv`/`hsvToRgb` 现已无引用（可删）。
`ant-color.js` 是静态文件，无需重建。
