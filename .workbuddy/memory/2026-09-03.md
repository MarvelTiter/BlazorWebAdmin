## 调研：路由/程序集扫描 ScanRazorLibraryAssembly 的 AOT 化可行性与 Razor 可见性实测

### 结论（已实测验证，非推测）

在临时目录搭了隔离探针工程（gen=netstandard2.0 源生成器 + app=Microsoft.NET.Sdk.Razor net10.0），实测结果：

1. **源生成器在分析阶段完全看不到 Razor 生成的语法树。**
   探针打印的 6 棵可见树：`Plain.cs` / `EmbeddedAttribute.cs` / `ValidatableTypeAttribute.cs` /
   `.NETCoreApp,Version=v10.0.AssemblyAttributes.cs` / `App.AssemblyInfo.cs` / `App.GlobalUsings.g.cs`
   —— 无一棵是 Razor 产物。`[Route]` 类只命中手写在 `.cs` 里的 `ProbeApp.PlainPage`，
   `@page "/probe"` 的 razor 组件一个都没找到。
   原因：.NET 6+ Razor 编译本身就是增量源生成器 `RazorSourceGenerator`；Roslyn 在所有生成器跑完后
   才把输出合并进 Compilation，因此生成器互相看不到对方产物。

2. **但生成器输出的代码里可以引用 Razor 生成的类型。**
   探针 emit 了 `typeof(global::ProbeApp.Components.Pages.TestRazorComponent)`，**编译 0 错误**。
   所有生成器的输出树最终在同一 Compilation 里一起绑定。
   ⇒ 可以从 razor 文件路径推算类型全名后放心 `typeof()`，且 AOT 下能硬引用 root 住类型防裁剪。

### 三条可选改造路线

- A. `AdditionalFiles Include="**/*.razor"` + `AdditionalTextsProvider` 文本解析 `@page`/`@attribute`/`@namespace`
     （复用仓库里 SvgContentClassGenerator 已有的套路）。业务页面零改动，但要写 mini razor 指令解析器。
- B. 把 `@page` 改成 `.razor.cs` 里的 `[Route]`，`@attribute` 改成真实特性。100% 等价、全保真，但要动 17 个文件。
- C. 混合：C# 语义树（全保真）+ razor 文本（兜底补 `@page`/`@attribute`）。推荐。

### ScanRazorLibraryAssembly 是另一个独立问题

```csharp
Assembly.GetEntryAssembly().GetReferencedAssemblies().Select(Assembly.Load)
item.ExportedTypes.Any(t => t.GetCustomAttribute<RouteAttribute>() != null)
```
- `GetReferencedAssemblies()` 裁剪后会少报；`ExportedTypes`+`GetCustomAttribute` 是运行时元数据反射，AOT 无法感知 → 页面类型会被裁掉。
- 正解不是"生成器扫描"，而是每个含页面的程序集自己生成注册代码：
  `[ModuleInitializer] static void RegisterPages() { AppConst.AddAssembly(typeof(页面)); RouteRegistry.Register(new RouteMeta{...}); }`
- ⚠️ 坑：`[ModuleInitializer]` 只在模块首次被访问时触发，主程序集必须显式触碰一次该程序集的某个类型。

### 用户决策（2026-09-03）：本次只留结论，不改代码

- **ScanRazorLibraryAssembly 的改造（Assembly.Load + ExportedTypes）：暂缓。**
- **路由元数据扫描（A 文本解析 / B 搬代码后置 / C 混合）：暂缓。**
- PagesService 的反射（`ExportedTypes` + `GetCustomAttribute<RouteAttribute>`）保持现状。
- 后续要动时，推荐从「C 混合方案 + 先做最小可跑 demo」切入。

## 方案：ModelPage.IsOverride 机制用源生成器 AOT 化（2026-09-03，仅方案未实施）

### 现状

`src/.../BlazorTemplate.ClientCore/Basic/ModelPage.cs:46`

```csharp
private bool IsOverride(string methodName)
{
    var method = GetType().GetMethod(methodName, BindingFlags.Instance | BindingFlags.NonPublic);
    return method?.DeclaringType != typeof(ModelPage<TModel, TQuery>);
}
```

`OnInitialized` 里调用 6 次，决定 `ShowExportButton` / `ShowAddButton` / `ShowImportButton`
以及是否挂接 `OnSelectedChangedAsync` / `OnCellUpdateAsync` / `OnRowUpdateAsync`。

三个问题：
1. **AOT 反射**：`GetType().GetMethod(name)` 依赖方法元数据，被裁则**静默返回 false**（按钮消失，不报错）。
2. **性能**：每次页面初始化 6 次按名字符串查找。
3. **语义缺陷**：用「是否 override」推断「功能是否可用」，但基类 `OnExportAsync` 有完整默认实现
   （刷新后返回 `Options.Result`），没 override 也该显示导出按钮，现在却恒为 false。

### 核心洞察：反转控制方向

基类在 ClientCore 程序集编译，**编译期看不到任何子类**——生成器不可能在基类里算出答案。
但反过来，生成器在**子类所在程序集**运行时能看到子类的完整语法（含 override 列表），所以把
「运行时查询」改成「编译期申报」即可 100% 静态判定。

### 推荐方案 A：基类留 virtual 钩子 + 生成器在子类生成 override

基类（ClientCore）改动极小：

```csharp
protected virtual void ApplyCapabilities() { }

protected override void OnInitialized()
{
    ...
    ApplyCapabilities();   // 取代 6 次 IsOverride
}
```

生成器为每个 `XxxPage : ModelPage<A,B>` 且含 `partial` 的类产出：

```csharp
partial class TestTable
{
    protected override void ApplyCapabilities()
    {
        Options.ShowAddButton      = true;              // 编译期常量
        Options.ShowExportButton    = false;
        Options.ShowImportButton    = false;
        Options.OnCellUpdateAsync   = OnCellUpdateAsync; // 方法组→委托，顺带 root 住方法
    }
}
```

- 钩子**无参**是关键：生成器不必解析 `ModelPage<A,B>` 的泛型实参，`Options` 在子类上下文里类型天然匹配。
- 判定逻辑：`INamedTypeSymbol` 沿 `BaseType` 链向上走到 ModelPage，收集满足
  `m.IsOverride && m.OverriddenMethod.ContainingType.ConstructedFrom` 是 ModelPage 的方法名
  （必须走继承链，中间基类 override 也算，语义才与 `GetMethod` 等价）。
- 若用户已手写 `ApplyCapabilities`，生成器跳过生成，避免重复 override。

**替代方案 B（不需要 partial）**：静态注册表 + `[ModuleInitializer]`，基类换成查表。
改动面更小（只换 `IsOverride` 方法体 + 6 个调用点改枚举），但有模块初始化器触发时机的坑。

### 边界与代价

- 方案 A 要求页面类加 `partial`。仓库现有 3 个子类（`TestTable` / `TestTaskList` / `OnlineUsers`）
  都是普通 `.cs` 非 partial，需逐个加关键字；可以用诊断（warning）提示漏加。
- 纯 razor 页面（override 写在 `@code{}` 里）仍是盲区——生成器看不到 Razor 产物，
  需保留手动兜底 API。
- 本次**未改任何代码**，用户明确要求"不需要代码落地"。

## 实施：ModelPage IsOverride + CollectButtons 生成器化（已完成并验证）

基类（`Basic/ModelPage.cs`）：
- `IsOverride` 6 次反射判定 → `protected virtual void ApplyCapabilities()` 空钩子（默认实现保留反射，作为 razor 兜底），`OnInitialized` 只调一次。
- `Options.Buttons = this.CollectButtons<TModel>()` → `protected virtual List<TableButton<TModel>> CollectPageButtons()`（默认实现仍是 `CollectButtons<TModel>()` 反射兜底）。

生成器（`ModelPageCapabilityGenerator.cs`，在 BlazorTemplate.ClientCore.Generators 内）：
- 沿继承链收集 override 的钩子 → 生成 `ApplyCapabilities` 重写（编译期常量 + 委托赋值）。
- 沿完整继承链收集 `[TableButton]`/`[EditButton]`/`[DeleteButton]` 方法 → 生成 `CollectPageButtons` 重写，
  **对象初始化器**形式（用户明确要求不传 Attribute 实例）：`new TableButton<TModel> { Label=..., Icon=..., ButtonType=..., Callback=方法组, LabelExpression=..., VisibleExpression=... }`。
  - EditButton 构造器只设 Label/Icon（不设 Danger，默认 false——用户纠正过），DeleteButton 设 Label/Icon/Danger=true；默认值在生成器里硬编码展开；未知派生特性 → MPCG003 警告 + 回退反射。
  - 拷贝语义与 `TableButton(options)` 构造器逐属性对齐：Label ?? "Button"、Type→ButtonType（总是写出，因 TableButton 默认 null）、Group ?? "TableTips.ActionColumn"、其余仅非默认值写出。
- 安全边界：一个按钮方法都没找到时不生成 CollectPageButtons（保护 @code 里声明按钮的 razor 页面）。
- 诊断：MPCG001 非 partial 警告；MPCG002 缺 Label/LabelExpression（运行时 ArgumentNullException 的编译期等价）；MPCG003 未知派生特性。
- 缓存结论：Callback 委托绑定当前页面实例，按类型缓存按钮列表不可行；生成代码本身就是编译期缓存。

验证（全部 --no-incremental 全量构建）：ClientCore 0 错误、BlazorAdmin.Client 0 错误；
生成产物核对 OnlineUsers/RolePermission/PermissionSetting(含 LabelExpression)/UserPage(泛型 TUser)/OperationLog/TestTaskList/TestTable 均正确。
补了 partial：RolePermission、OperationLog（OnlineUsers/TestTable/TestTaskList 上一轮已补）。

踩过的坑：
1. 生成器项目（netstandard2.0）不能引用宿主类型：`nameof(ClientCore类型.成员)` 和 KeyValuePair 解构都不可用，属性名用字符串字面量。
2. `SymbolDisplayFormat.FullyQualifiedFormat` 自带 `global::` 前缀，手动再拼会出现 `global::global::`（CS7000），比较时两边必须一致。
3. `dotnet build` 不加 `--no-incremental` 会复用旧产物报"假绿"。

## WPF 构建失败定性（解决方案级 33 错误的 Wpf 部分，已查清）

- `BlazorAdmin.Wpf` **主编译 0 错误**（Package 模式 `-p:CurrentMode=Package`）；全部错误都在 WPF 标记编译临时工程（`*_wpftmp.csproj`）里。
- 临时工程丢失 ClientCore 传递引用：`LocalAuthService.cs` 用到的 `UserInfo/UserPwd/LoginFormModel/QueryResult` 全在 ClientCore，经 AppServer 包（nuspec 声明依赖 ClientCore）传递，主编译可见、wpftmp 不可见 → WPF markup compile 的传递引用问题。
- 版本错位：projects.versions.props 里 AppServer/AntUI 钉在 2026.08.31.1，ClientCoreVersion=2026.09.03.1；全局缓存里 clientcore 最高只有 2026.9.2.1，但 Wpf assets 解析出 2026.9.3.1（今日构建的包从未 pack/push 到 LocalNuget 源，源里只有 2 个旧包）——restore 状态不一致。
- 结论：与生成器改造无关，是 WPF 临时工程 + 本地包源陈旧的组合问题。修复方向：跑 local-pack.ps1 把最新包 push 进源再 restore；或升级 SDK 看 wpftmp 传递引用是否修复。
